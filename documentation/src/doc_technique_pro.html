1. Présentation du projet

Savora est un système de réservation pour restaurant composé de trois parties qui partagent une même base de données PostgreSQL :

PartieÀ quoi ça sertQui l'utilise
Site web (client léger)
SvelteKit + Drizzle		Présenter le restaurant et réserver une table en ligneLe client
API REST
FastAPI + SQLAlchemy		Point d'entrée du client lourd vers la base(interne)
Application bureau (client lourd)
Python + CustomTkinter		Gérer les réservations, les clients et les placesLe personnel

1.1 Schéma de l'architecture

Le site web écrit directement dans la base avec Drizzle. L'application bureau passe par l'API. Les deux utilisent la même base : une réservation faite sur le site apparaît aussitôt côté personnel.

2. Mise en route et démonstration

Cette partie explique comment lancer le projet et comment faire une démonstration complète.

2.1 Lancer le projet

On ouvre plusieurs terminaux, dans cet ordre :

① Base de données (PostgreSQL) 
sudo service postgresql start      → base « savora » sur le port 5432
② API REST (pour l'application bureau) 
cd savora_api
uvicorn main:app --reload          → http://localhost:8000/docs
③ Site web 
cd "Client Leger"
npm run dev                        → http://localhost:5173
④ Application bureau (personnel) 
cd savora_desktop
python main.py

2.2 Visualiser la base — Drizzle Studio

Drizzle fournit une interface web pour voir et modifier la base très simplement. On la lance dans un terminal dédié :

cd "Client Leger"
npm run db:studio                  → https://local.drizzle.studio

Dans le navigateur, on voit les trois tables du projet (reservations, clients, daily_quotas). On peut cliquer sur une table pour afficher son contenu, ses colonnes et ses liens.

À montrer au jury : Drizzle Studio est la façon la plus simple de prouver que les données sont bien enregistrées en base après une action.

2.3 Scénario de démonstration (3 étapes)

ÉtapeActionRésultat visible

5. Comment ça marche (l'essentiel)

5.1 Le site web et Drizzle

Quand un client réserve, le site enregistre la réservation directement dans PostgreSQL avec Drizzle. Exemple simplifié de l'insertion :

// le site insère la réservation dans la base
await db.insert(reservations).values({
  partySize, date, timeSlot, mealPeriod, ... , status: 'pending'
});

Le site calcule aussi les places restantes (avec Drizzle) pour griser les créneaux complets. Aucun e-mail n'est envoyé : la réservation reste « en attente » jusqu'à validation par le personnel.

5.2 L'application bureau (MVC)

L'application du personnel est organisée en MVC (3 rôles séparés) :

RôleFait quoiFichier
ContrôleurCoordonne l'écran et les actionsmain.py
VuesLes écrans (planning, détail, clients, quota)components/
ModèleParle à l'API RESTapi_client.py

Toutes les actions (valider, refuser, modifier…) passent par l'API, qui applique les règles et enregistre dans la base.

5.3 La règle des places (quota)

Avant d'enregistrer une réservation, on vérifie qu'il reste de la place. Si le service est complet, la réservation est refusée.

if (couverts_réservés + nouveaux_couverts > maximum) {
    refuser ;   // service complet
}
Phrase simple à retenir : « Le site écrit dans la base avec Drizzle, l'application bureau passe par l'API, et les deux partagent la même base PostgreSQL. »

RisqueProtection mise en place
Injection SQLOn n'écrit jamais le SQL « à la main » : Drizzle et SQLAlchemy génèrent des requêtes sûres
Trop de réservationsVérification du quota : refus si le service est complet
Données invalidesContrôles avant enregistrement (couverts 1–6, date non passée, e-mail valide)
